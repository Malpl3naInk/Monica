# 数据模型、落盘与降级边界

本文件是待实施的方案，不能当作已实现的兼容承诺。源码证据见 [source-review.md](source-review.md)。

## 1. 原始项目与组件

项目是一个有独立身份、归属、版本和回收状态的聚合。物理上可以分块保存正文、附件和密钥；「同一个项目」不要求所有字节挤进一条 SQL 记录。所有组件写入都经过项目仓库，不能让笔记仓库和密码仓库分别拥有可互相覆盖的主副本。

建议的逻辑结构：

    UnifiedItem
      itemId: UUID
      storageScope: database identity + folder + access policy
      title, icon, favorite, lifecycle
      primaryComponentId
      components: [{ id, kind, label, order, data, relations, extensions }]
      attachments: [{ id, componentId?, contentRef, ... }]
      revision, extensions

组件种类包括 login、otp、passkey、note、ssh、gpg、apiToken、barcode、wifi、card、identity、address、paymentAccount。它们是新领域层的类型，不写成旧 Room ItemType 的新枚举值。格式标识建议为 `monica.unified-item.v1`，命名空间最终须与桌面/扩展作者核对，不能声称当前各端已支持。

身份与关系规则：

- 全部身份都是带数据库作用域的稳定 ID，不以标题、列表位置、可重复的用户名或哈希 Long 作为主键。
- 列表入口使用 `(storageScope, itemId, componentId, viewKind)`。同一项目两个 note 有两个入口，但同一个 itemId。
- OTP 与账号通过 loginComponentId 显式关联，不能按同名或「第一个密码」猜测。Passkey 保留 credential ID / RP ID / provider 作用域及既有私钥引用。
- 组件可以有自己的显示名和笔记标签；收藏、文件夹、共享权限、回收状态先统一属于项目。原本独立的权限不同，就不能自动合并。
- 备注与笔记区分：一条短备注仍是属性；新建独立阅读内容才是 note 组件。不要将所有旧备注自动投影到笔记列表。
- 未识别组件保留原始结构，并显示「此版本暂不能编辑这部分」；编辑其他内容不能丢弃它。解析失败不能变成空列表。
- 外部引用是引用，嵌入组件是自有内容；引用必须显示来源。旧 boundNoteId 不等于该笔记已经被项目拥有。

主组件只决定兼容存储和默认打开位置。各列表展示按组件存在与否决定，不能只按主组件过滤。修改项目标题不应自动覆盖用户为两篇笔记分别起的名称。

## 2. 列表与写入

只提供项目仓库这一条写入入口。类型专用编辑器产生对组件的补丁，并提交 itemId、componentId、baseRevision 与 operationId。

    原数据库 / 兼容记录
            ↓ 读取适配
       UnifiedItem 快照
            ↓ 按需投影
       密码 / 笔记 / 验证器 / 卡包列表
            ↓ 项目与组件 ID
       共用详情 / 笔记等专用详情
            ↓ 组件补丁 + 基准版本
       项目仓库 → 后端适配器 → 同一原始项目

列表摘要不携带密码、私钥、完整长文、图片字节。打开详情只读取当前项目；展开私钥/长文才获取对应敏感内容，不等待 WebDAV 上传或全库解密。可重建索引不能成为主数据，失效时只重建变化项目。

本轮目标不是为每个 note 写一条独立 SecureItem 再用外键连接。若旧服务暂需 Passkey/自动填充查询索引，可以保留派生兼容记录，但必须由项目仓库单向维护，不能仍有直接 DAO 写入绕过项目。

整个应用接入前不得放开混合项目写入；否则新建页能保存，旧的批量移动、去重、回收站或导入就可能破坏同一项目。

## 3. 本地：不提高 Room 版本的推荐路径

目前没有可供所有实体安全共享的扩展列：PasswordEntry、SecureItem、PasskeyEntry 分表，自定义字段仅属于密码。为了绕过这一点，伪造密码记录来承载纯笔记、复用 sshKeyData 存任意数据、把秘密放进普通 notes，都不采用。

推荐先验证「已有主记录 + 独立加密扩展存储」：

1. 已有主记录继续保存原本能表达的主组件，纯笔记仍用原笔记记录，纯 Passkey 保留现有安全存储。主字段只有一个权威值，不在扩展中再维护另一份可写值。
2. 项目的组件目录、稳定 ID、新增组件与必要关联放入应用私有的加密扩展块，按项目读取。它是项目的组成部分，不是一组独立可编辑的子项目。
3. 用带数据库实例作用域的身份绑定将扩展块绑定到原始记录。Room 数字 ID 仅作定位，不单独作为跨恢复身份。第一次结构性保存时持久化稳定绑定；只读访问不写库。
4. 扩展存储也有格式版本、密钥生命周期与备份清单。这里承诺的是不提升 Room schema 78，绝不是「存储格式完全没变」。
5. 大正文与附件分块且认证加密，密钥材料使用现有安全存储；不得仅依赖 isProtected 布尔值、Base64 或隐藏 UI 充当加密。

原型必须先解决的事务问题：

- Room 与扩展文件不是同一事务。采用加密写入意图与代际快照：先持久化待提交内容和基准，再更新主记录，最后发布扩展版本。读者只读取已发布的一致版本。
- 崩溃恢复比较已提交记录、原/目标版本与操作回执；无法判定时保留两个版本待恢复，不用时间戳猜赢家。
- 旧版仍能修改主记录。再次升级时按基准比较主字段的变化，只更新对应主组件；扩展内容不因为旧版不知道它就被清空。
- 旧版恢复备份可能复用 Room ID，旧版彻底删除也可能留下扩展块。不能把它自动挂到恰好同 ID 的新记录，更不能复活用户删除的项目。身份不确定时隔离为可恢复内容。
- 新版导入、导出、卸载前备份和迁移必须包含扩展与身份映射；旧版生成的 ZIP 不理解新扩展，不能保证包含它。

这是推荐验证路径，尚无事务/身份原型或测试结果。如果原型无法满足崩溃恢复、性能与身份要求，应改用明确的统一存储迁移，并提供降级导出；不能为了维持版本号强上易丢数据的方案。

## 4. KeePass / KDBX

一个原始项目对应一个 KDBX Entry，保留 UUID、分组、标准字段、保护属性、附件及历史。主账号继续映射 Title / UserName / Password / URL / Notes；主 OTP 和适用的 Passkey 使用既有兼容字段。

其他组件放在命名空间明确的扩展字段/加密附件中，建议目录键 `Monica.UnifiedItem.v1`。这只是候选契约，不假定其他 KeePass 客户端能解析目录。含敏感数据的扩展使用 KDBX 保护字符串或数据库内附件，不能放到数据库外的明文 sidecar。

读写要求：

- 从完整原 Entry 打补丁，只移除明确属于本次修改的字段；保留未知字段、附件、Auto-Type、模板和历史。
- 同一项目有两篇笔记，不产生两条 KDBX Entry。KeePass 客户端仍可看到标准主字段及扩展，不能承诺出现两篇原生笔记。
- 不更换原 KDBX 容器版本、KDF、密钥文件或加密参数来配合新界面。
- 当前普通字段补丁有保留未知字段的基础，但原生字段编辑存在 replaceAllFields。这个路径和历史恢复、合并、导出必须单独验证。
- 外部客户端修改主密码时，重新读取同一 Entry 并合并到主组件；外部客户端删除扩展、把扩展替换为空或恢复旧历史时，显示内容差异，不静默补回。

## 5. MDBX / MDBX2

新领域「项目」不是当前 MDBX 的 project/collection 文件夹；一个统一项目应对应其中的一个逻辑 object/entry。不得把一个集合的所有密码错误合成一个项目。

推荐保留主对象物理 ID、逻辑 ID、原 entryType 与可被旧端解析的主字段，扩展目录承载余下组件；大内容通过该对象拥有的加密附件/内容块保存。新旧 schema 的读取、签名指纹和 commit 行为须在 Android 适配层定义。

已确认的限制：

- 现有 Android passwordMutation / secureItemMutation / passkeyMutation 从已知字段重新拼 payload；未知外层字段不天然保留。必须先补原始载荷透传与版本合并，再开放扩展写入。
- **16 KiB 是 Android 与 CLI 的 Token 通道限制，不是 MDBX 引擎的统一存储上限。** Android ApiTokenPayload 和显式 revealObjectWithLimits 使用这个值；CLI 的 gateway 读取也限制为 16 KiB，StoredCredential 还使用 deny_unknown_fields。因此即使总量不足 16 KiB，也不能往 gateway JSON 随意添加统一项目字段。
- 本地 MDBX Rust 源码的通用对象读取默认允许 8 MiB、可选硬上限 64 MiB；写入单命令默认 1 MiB、硬上限 16 MiB。读取和写入限制不同，这些源码值也不等于已确认每个历史 APK 都携带同一引擎。
- Android **已有** NativeApiTokenExtrasStore：通过对象 label/assignment 保存附加资料，ApiTokenMetadata 当前上限 64 KiB，单独读取且检查重复副本。因此先验证复用/扩展这条路径和附件机制，不直接提高 Token 通道限制，也没有证据证明本任务必需修改 MDBX 引擎。
- 普通 label 可以复用，不能未经约束就充当统一组件所有权。若沿用此载体，必须验证私有附加资料的加密与授权、唯一归属、删除/移动/冲突、原子写入、备份和旧客户端保留。64 KiB 同样不是无限长笔记的方案；大正文另用所属项目的加密内容块。
- 混合项目中的 API Token 不会自动出现在尚不识别该组件的 CLI/扩展中。不能偷偷创建第二个可写 Token 对象来伪装兼容。本轮不修改 CLI；未通过能力检查的 gateway 混合写入保持关闭。
- 保留批次按条数、payload 字节和 intent 字节共同限流；不能把整个库当成一次 Kotlin → Rust 的巨型字符串。
- 无内容变化不得产生 commit；使用统计、OTP 秒数、展开/收起不属于项目内容变更。

必须区分 legacy MDBX 与 MDBX2，以及 Android 携带的具体引擎构建；检查根目录 Rust 源码不能代替检查 APK 实际桥接版本。需要改 MDBX 源码的条件、涉及模块和替代方案列在 [待审阅取舍](decisions.md)，本轮均未执行。

## 6. Bitwarden

原生 Cipher 有一个 type；Login 的 username/password/totp 为单值，fido2Credentials 为列表。一个 Cipher 不能同时成为原生 Login、Card、SSH、SecureNote。

因此采用两级能力，而非承诺「全部原生通用」：

| 情况 | 存储与呈现 |
|---|---|
| 一个主登录及适用的 OTP/Passkey | 用原生 Login / fido2Credentials；保留现有互操作能力 |
| 主卡片、主笔记或 SSH 等单类项目 | 用其对应的原生 Cipher 类型，支持程度依服务端能力 |
| 同一项目额外账号、两篇笔记、二维码等 | 在经验证的加密扩展字段/附件中保存，Monica 可解析；官方客户端主要编辑原生部分 |
| 项目超过该账号/服务端扩展或附件能力 | 保存前明确说明哪些内容不能存，保留草稿，改目标或由用户选择拆成独立项目 |

扩展字段建议命名空间 `monica.unified-item.v1`，作为候选协议。必须核对字段大小、字段数、整 Cipher 限制、组织权限及附件权限；本轮没有服务端限额验收，不能拍脑袋设置一个适用于所有自托管实例的限额。

主登录和原生 Passkey 数据不在扩展内再保存一套可独立修改的副本。扩展只保存目录、关系及原生无法表达的内容。使用当前 Cipher key/组织密钥加密，不把 Android Keystore 密文直接当作跨设备 payload。

同步时获取完整基准，保留父 Cipher、其他凭据、未知字段、附件及无关队列。按服务器实际支持的版本检查提交；无可靠版本检查时不能许诺并发安全。当前代码中有字段合并分支，但不代表全部字段/所有实体上传都已达到此要求。

官方客户端若编辑原生主密码，再回到 Monica，应更新主组件并保留两篇扩展笔记；若官方客户端删除扩展字段，则需要恢复/冲突处理。把大 JSON 作为可见长备注不是解决方案。

## 7. 降级承诺分层

| 层级 | 本方案目标 | 不能推导出的结论 |
|---|---|---|
| 数据库可打开 | 尽量保持 Room 78 和原容器版本、旧枚举/主类型 | 不等于任意历史 APK 都能安装、打开现有库 |
| 旧端可见 | 主组件保持原格式；新增组件可能不可见 | 不等于旧端拥有多笔记、多账号详情 |
| 旧端普通编辑 | 对确认保留扩展的兼容基线做定向验证 | 不等于旧端的合并、迁移、删除、全字段替换、备份都安全 |
| 降级往返 | 新→兼容旧端→新，保留主字段与扩展差异 | 不等于损坏/被删除的扩展能无中生有恢复 |

建议先发布不写新结构的「兼容准备版本」，具备未知数据保留和基础识别；写入版仅承诺退回经过验收的兼容版本。更旧版本通过「导出兼容副本」降级：明确拆分混合项目，并保留原格式加密备份。拆分会失去同源联动，应在操作摘要说明。

Android 系统本身可能限制 versionCode 降级；这与数据格式兼容分别说明。不能用卸载重装作为保持数据的默认降级步骤。

## 8. 老数据转换

第一次读取时虚拟包装为单组件项目；确定身份后展示新详情，不修改数据库版本、时间戳、统计或同步队列。稳定身份优先来自原后端 UUID/credential ID，再结合数据库作用域；不在每次读取时随机生成新 ID。

原有独立笔记/OTP/Passkey 绑定仍保持外部引用。只有同库、权限与所有权明确、引用完整可迁移时，才提供「移入此项目」：

1. 展示将纳入的内容及受影响的其他引用。
2. 写入并验证目标项目，保留操作回执。
3. 更新所有索引/旧引用；再归档被移入的独立来源，失败时保留来源可恢复。

共享给其他项目的笔记、跨库绑定、设备绑定密钥、不可迁移 Passkey 不自动吸收。批量创建过的账号和 replicaGroupId 副本也不能仅因同名就合成一个项目。

## 9. Passkey 与安全语义

项目化改变组织方式，不改变签名与网站身份。credential ID、userHandle、RP ID、算法、私钥引用/材料、BE/BS、signCount、真实 provider 归属和迁移策略保持原样。设备绑定私钥允许安全引用，不要求导出后塞入通用 JSON。

创建 Passkey 仍来自系统 Credential Manager 的网站注册流程，或合规导入；「添加内容」提供接收/选择已有合法凭据，不用表单随意生成一个网站可登录的 Passkey。凭据交换继续跳过规范不允许迁移的非零计数凭据，不能借项目导出绕过。

自动填充、无障碍和键盘填充候选以账号组件为单位，OTP 绑定明确账号，Passkey 继续按 RP/credential/provider 作用域选取。通过统一仓库更新使用统计，内容指纹排除统计；不能因为一次填充写回旧整行覆盖其他组件。

组件脱离原项目不自动撤销网站的 Passkey；删除本地材料与撤销网站注册分别说明。
