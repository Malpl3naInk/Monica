# 需要你审阅的取舍

这些是设计选择与风险，不是已获准实施的变更。本轮只做方案与 M3E Canvas；没有修改 Android、CLI、MDBX 引擎或 F-Droid 代码。

## 1. 16 KiB 不该直接作为「改 MDBX 引擎」的理由

已核对：

| 位置 | 当前限制/行为 | 意义 |
|---|---|---|
| Android ApiTokenPayload 与 Token reveal | 16 KiB | Token 专用读取/校验预算 |
| CLI gateway | 16 KiB 且拒绝未知字段 | 不仅是大小；随意追加字段也会破坏互操作 |
| Android Token 附加资料 | 独立 label/assignment；64 KiB | 现有备注/自定义字段已经避开严格 gateway payload |
| 本地 MDBX Rust 通用对象读取 | 默认 8 MiB，可选硬上限 64 MiB | 引擎不是只能存 16 KiB；这是披露边界，非整库容量 |
| 本地 MDBX Rust 单命令写入 | 默认 1 MiB，硬上限 16 MiB | 写入、读取、批次限额各自不同 |

**推荐**：纯 gateway Token 的小载荷保持原协议，新混合内容优先评估已有附加资料/附件接口。不能先放大所有读取限额来掩盖数据组织问题，也不能把长文都塞进 label 后称为无限扩展。

**需要评审的代价**：如果要求 CLI/扩展也能发现任意项目中嵌入的 Token，需要这些客户端显式支持组件协议。只在 Android 解析出 Token，不会自动改变其他客户端。保持独立主 Token 的项目可以继续走原通道，但将它变成另一个主项目里的组件必须重新审查协议与权限。

## 2. 哪些情况下才需要改 MDBX 源码

| 需求 | 先做什么 | 可能涉及源码 | 当前判断 |
|---|---|---|---|
| 保留新目录/未知字段 | Android 从原 payload 打补丁，使用现有元数据/附件接口 | Android Mdbx2Repository、NativeApiTokenExtrasStore、组件 adapter | 首先是 Android 适配工作，没有证据必需改底层格式 |
| 现有 Token 的更多 Android 资料 | 验证附加资料唯一归属、读取权限、删除/移动与容量 | Android ApiTokenMetadata / NativeApiTokenExtrasStore | 可先用现有能力做设计原型；不是批准增大限额 |
| 跨平台的项目/组件目录、增量摘要 | 确认现有分页/summary API 能否满足；摘要不得披露秘密 | mdbx-storage 的 summary/read 边界，mdbx-ffi；Android 桥接 | 只有现有接口无法表达或测得确有瓶颈时再提出变更 |
| 组件和附件无法一起原子发布 | 先验证现有 write-command group / operation coordinator | mdbx-storage/repo/operation_coordinator.rs、mdbx-ffi/write_facade.rs | 原型未做，不能认定必须修改 |
| 私有扩展借 label 无法保证权限/级联生命周期 | 先核对元数据授权和所有权；换用所属对象的加密内容块 | mdbx-storage 的 metadata disclosure/attachment/lifecycle 模块及 ffi | 如果现有表达不了，需单独设计底层契约，不能直接复用共享标签语义 |
| 放大 gateway Token 上限或允许新字段 | 同时审查 Android、CLI、老版本读写与内存预算 | ApiTokenPayload、monica-pass-cli/src/vault.rs；不必然涉及引擎 | 不推荐作为统一项目的默认方案 |
| 新建底层对象类型/提高文件格式版本 | 比较可扩展旧类型的方案并提供降级导出 | mdbx-core/model、storage migration、ffi、所有 reader | 暂不采用；兼容代价最大，需要你先审阅具体提案 |

如后续确需修改 MDBX，会先列清：目标仓库和文件、旧接口不足的复现/测量、变更后的协议、旧端行为与迁移/恢复方案。不会把「用 Rust 优化」理解为允许直接重构数据库引擎。

## 3. 不升 Room 版本，也不是零代价

**推荐候选**：已有主记录保留，加密扩展块保存其他组件；不添加新 ItemType 或把秘密塞进备注。

**不理想之处**：两个持久化位置带来崩溃一致性、身份绑定、旧版删除/恢复识别、备份遗漏风险；独立扩展本身仍有新格式。只有原型证明这些问题可控，才比一次清楚的数据库迁移更划算。

**替代方案**：明确引入统一存储与迁移，提供完整备份和兼容导出，接受老版本无法直接读写全部新内容。不能同时保证任意混合数据、任意旧版完整编辑、以及完全不改变存储语义。

## 4. Bitwarden 官方 UI 不能自动变成 Monica 的统一项目 UI

**推荐**：主账号保持原生 Login/Passkey 互操作，余下组件用经验证的加密扩展承载。选择数据库时可查看哪些部分是原生显示、哪些由 Monica 展示。

**不理想之处**：其他客户端可能只显示主账号，额外笔记或 SSH 不会自动成为多个原生条目。字段/附件限制、组织权限还需验证。

**替代方案**：拆成多个 Cipher，可提高各类型的原生可见性，却不再是「一份原始项目」。只能由用户明确选择兼容导出/拆分，不能后台偷偷拆开。

## 5. 老绑定不会全部自动变成项目组件

**推荐**：独立旧数据自动获得统一读取外观，不写库；同库且归属明确的旧绑定可按需移入。

**不理想之处**：共有笔记、跨库绑定、设备绑定私钥不能无条件吞并。需要保留外部引用，或先选择移入/复制/保持关联。

**替代方案**：按绑定关系批量强制吞并虽然界面看起来统一，但容易改权限、切断其他引用或丢掉真实 provider 归属，不采用。

## 6. 关闭试用与降级不是同一件事

**推荐**：开关控制新建入口；已有混合项目一直能打开，不能关掉后回到只理解主字段的旧写入路径。APK 降级仅承诺经过测试的兼容基线，更旧版本使用兼容副本。

**不理想之处**：旧端完整备份不一定包含扩展；用户也不能期待旧端拥有多组件编辑能力。UI 应把这些说明放在试用说明与降级操作里，普通新建不堆满技术警告。

## 7. 页面与批量语义

按最新反馈，选择控件放在大标题下，用紧凑居左的名称＋箭头按钮组，随正文滚动；下滑后「新建密码」收进顶栏。追加内容、URL 和应用按钮同样缩至内容宽度并靠左。统一项目使用「模板」，上一版独立编辑器使用「类型」，二者视觉一致但语义不同。

「添加账号」在当前项目追加组件；「批量新建」创建多个独立项目。公共信息是创建默认值，并非之后永远共享的实时字段。这个区分是为了避免编辑一个账号意外改掉整批账号。

这里列出的是推荐方案，待你审阅；并不在本轮开始实现这些存储变更。
